# 级联故障推演工具（cascade）

针对"下游只是慢了一点，却被上一层层的重试打死"这类配置事故的**核查 + 推演**工具。

它模拟一家 300+ 服务的公司，每个调用方对每个下游都有自己的超时、重试、退避，
分别散落在**代码注解**、**配置中心**、**服务网格**三处，有的互相覆盖，有的没配走默认。
工具把这些合并成"每条边最终生效的行为"，沿调用链找出**超时倒挂**和**重试放大**，
再按时间步进推演故障如何在全链路放大，并用逐请求离散事件模拟核对倍数。

## 快速开始

```bash
pip install flask pytest          # 仅需 Flask；numpy/playwright 可选
python3 -m cascade                # 启动 Web，默认 http://127.0.0.1:5000
python3 -m cascade --port 5055 --seed 20241118

python3 -m pytest tests/ -q       # 25 项测试
python3 -m cascade.cli overview   # 无界面：公司概览
python3 -m cascade.cli incident   # 复现上周故障
python3 -m cascade.cli verify     # 三方核对
```

## 六个要求如何实现

### 1. 三来源配置合并（`cascade/resolve.py`）

三个来源分属两个**运行时层**：

| 来源 | 层 | 作用 |
|------|----|----|
| `code` 代码注解 | 应用层 | 客户端硬编码兜底 |
| `config_center` 配置中心 | 应用层 | 运维动态下发 |
| `mesh` 服务网格 | 基础设施层 | Sidecar 在进程外执行 |

合并规则：

* **层内覆盖**：应用层里配置中心 > 代码注解；同一来源内精确匹配 > 通配 > 全局。
* **跨层叠加**：
  * **超时取 `min`** —— 两层是串联的两个计时器，谁先放弃谁生效。
  * **重试相乘** —— 应用层 `r_app` 次、网格层 `r_mesh` 次时，
    一次上游调用最多打到下游 `(1+r_app) × (1+r_mesh)` 次。**这就是放大倍数的来源。**
* 三层都没配的字段落到框架默认（超时 1000ms、重试 0）。

`/api/edge/<id>` 返回每个字段的**最终值与来源**，把"为什么是这个值"讲清楚。

### 2. 超时倒挂（`cascade/analysis.py`）

一条边的最坏耗时 = `尝试次数 × 单次超时 + 全部退避`。
若它 > 上游愿意等的时间（入口看 SLO，中间层看调用它的那条边的超时），即为**倒挂**：
上游早已放弃，下游还在重试，`空转时长 = 下游最坏 − 上游预算`。

### 3. 重试放大（`cascade/analysis.py`）

沿调用链枚举到叶子的路径，最坏放大 = `Π(每跳尝试次数)`，
并标出连续重试、倒挂叠加的"危险层数"。

### 4. 时间步进推演（`cascade/sim_stepped.py`）

按 `dt` 推进，每 tick 依次处理：入口到达 → 退避到期 → 处理完成 → 调用超时 →
预算中止 → 空闲 worker 准入。关键建模：

* 一次调用从开始到结束**一直占着 worker**（阻塞式客户端），等待期间线程不释放 ——
  这是"线程池被打满"的真实机制。
* 超时后调用方放弃，但**被调用方继续干活**（孤儿请求），
  除非该边配了 `propagate_deadline`。孤儿 + 重试正是放大来源。
* 队列有上限（worker 的 8 倍），溢出即快速拒绝，模拟连接池打满。
* 输出逐帧快照，页面用来**一步步播放**流量放大的过程。

### 5. 修改建议 + 改完再推演（`cascade/recommend.py`）

每条建议都是对三来源配置的**真实改写**（以最高优先级"建议方案"规则叠加），
于是可以重新解析、重新推演，用数据证明有效：

| 建议 | 做法 |
|------|------|
| 只在最内层重试 | 外层重试清零，只在每条链最内层留一次 |
| 超时逐层递减 | 每跳超时 ≥ 下游正常耗时 × 1.6，并打开超时传递 |
| 加重试预算 | token bucket，重试 ≤ 首发的 10% |
| 网格与应用不同时重试 | 同一跳只留一层重试，去掉相乘 |
| 组合方案 | 上面三条叠加 |

### 6. 上周故障复现（`cascade/scenario.py::scenario_from_incident`）

`gateway-01 → bff-orchestrator → order-service → inventory-service`：

* 网关 3s 总预算；bff 对 order 设 5s 且应用重试 3 次，网格层又叠 1 次（共 8 次尝试）；
  order 对 inventory 设 2s、重试 2 次（共 3 次尝试）。
* inventory 正常 1.2s，变慢 2.2 倍到 2.6s → 超过 2s 超时 → 触发重试连锁。
* 4rps 入口被放大到 **18 倍**，远超 inventory 16rps 容量 → 队列打满、大量拒绝。

一键复现：页面右上角"复现上周故障"，或 `cascade.cli incident`。

## 核对：三方差值必须对得上

推演的倍数要用**逐个请求的离散事件模拟**核对（`cascade/verify.py`）。
两个引擎实现独立，只共享配置策略函数（`cascade/policy.py`）：

| 引擎 | 时间 | 用途 |
|------|------|------|
| `sim_stepped` | 固定 dt 量化 | 动画播放 |
| `sim_des` | 连续精确事件堆 | 核对倍数 |

**收敛工况**（固定请求数、发完排空到静止、确定性时长、无饱和）下，
解析公式、步进推演、离散事件三者的放大倍数**精确相等**：

```
gateway→bff       解析 ×1    步进 ×1    离散事件 ×1
bff→order         解析 ×8    步进 ×8    离散事件 ×8
order→inventory   解析 ×24   步进 ×24   离散事件 ×24
```

页面"核对"标签页展示这张表（最大相对偏差 0）。

## 页面

* **拓扑图**：SVG 绘制，倒挂边红色虚线、事故链粉色、有重试的边黄色；
  默认只显示事故链邻域，可切换"倒挂子图 / 问题子图 / 全公司"。
  点边看三来源配置合并，点节点选为故障点。
* **推演播放**：时间轴拖动或播放，节点用占用环、过载脉冲表示负载，
  边按窗口流量加粗变色，直观看到流量如何一层层放大。
* **右侧面板**：配置解析 / 倒挂 / 放大分析 / 推演结果 / 修改建议 / 核对。

## 目录

```
cascade/
  model.py        服务、边、三来源配置、默认值
  resolve.py      三来源合并（层内覆盖 + 跨层叠加）
  generator.py    300+ 服务的"乱"公司 + 硬编码事故链
  analysis.py     调用链枚举、倒挂、放大
  policy.py       超时/退避/处理时长（三引擎共用）
  scenario.py     故障注入、聚焦子图
  sim_stepped.py  时间步进推演（播放用）
  sim_des.py      逐请求离散事件模拟（核对用）
  verify.py       三方核对
  recommend.py    修改建议（可执行的配置改写）

tools/ui_check.py Playwright 端到端 UI 检查（可选）
```

## 关键设计取舍

* **两个模拟器故意各自实现调度**，只共用策略函数，这样核对才有意义 ——
  若共用调度，差异会被掩盖。
* **重试预算是运行时封顶**，静态解析出的最坏次数不变，但推演中重试被 token bucket 挡住；
  建议页对这两种效果分别标注。
* **"饱和"不等于"很忙"**：变慢的服务占用率会很高，但只要队列没积压、没有拒绝，
  就没被打垮 —— 这正是"改前被打死 / 改后只是慢"的区别。
